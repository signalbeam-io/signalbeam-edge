# Onboard an EdgeAgent (Raspberry Pi) against the cloud control plane

Register a device, get it heartbeating, and reconcile a bundle assignment end-to-end
against a deployed SignalBeam control plane (e.g. the North Europe ACA dev stack).

> Variables used below:
>
> - `GATEWAY` — the API gateway URL, e.g.
>   `https://sb-ca-apigateway-dev.whitesea-94fe530f.northeurope.azurecontainerapps.io`
> - `TENANT_ID` — your tenant UUID (dev default: `00000000-0000-0000-0000-000000000001`)
> - `TOKEN` — a registration token (`sbt_…`), generated by an operator (see step 2)

## How the agent onboards

Cold-start sequence the agent performs (all HTTP to `GATEWAY`, plus optional NATS):

1. `POST /api/devices` — register `{ tenantId, deviceId, registrationToken, hostname, platform }`.
   Tenant is derived from an authenticated API key when present, otherwise taken from the body
   (the anonymous registration handshake). Returns `status: Pending` (or `Approved` with an auto-approve token).
2. `GET /api/devices/{id}/registration-status` — polled every `RegistrationPollIntervalSeconds` (default 300s) until approved.
3. `POST /api/devices/{id}/claim-key` — once approved, exchange the registration token for the device API key (`sb_device_…`), stored in `device-credentials.json` (chmod 0600). The token is then cleared.
4. `POST /api/devices/heartbeat` (X-Api-Key) — every `HeartbeatIntervalSeconds` (default 30s), with CPU/mem/disk metrics. Also published to NATS `signalbeam.devices.heartbeat.{id}` when reachable.
5. `GET /api/devices/{id}/desired-state` (X-Api-Key) — every `ReconciliationIntervalSeconds` (default 60s); the agent pulls/starts/stops containers to match, then `POST /api/devices/{id}/reconciliation-status`. A NATS push on `signalbeam.bundles.assignments.{id}` triggers immediate reconcile.

Config: `Agent:CloudUrl` (`--cloud-url`), `Agent:CredentialsDirectory` (default `/var/lib/signalbeam-agent`), intervals in `appsettings.json` or `Agent__*` env vars.

## Pre-flight: verify the control plane is serving

```bash
# Gateway up?
curl -sS --http1.1 "$GATEWAY/health"                 # -> Healthy
# DeviceManager routed + auth enforced?
curl -sS --http1.1 "$GATEWAY/api/devices"            # -> 401 MISSING_CREDENTIALS
```

> **Use HTTP/1.1** when probing by hand — the ACA ingress can throw an
> `HTTP/2 framing layer` error on some clients; `--http1.1` avoids it.
>
> **Scale-to-zero cold starts:** internal services (DeviceManager, IdentityManager) idle to
> zero. The first request after idle can take 10–30s while the container starts. If a probe
> times out, retry once. Device registration tolerates a cold IdentityManager via a retrying
> quota check (see [#390](https://github.com/signalbeam-io/signalbeam-edge/issues/390)).

## 1. (Operator) Generate a registration token

Minting a registration token is an **operator** action, so it requires a Zitadel/OIDC JWT
(`Authorization: Bearer <jwt>`) — the dashboard already sends one. Grab a token from the dashboard
session (or an OIDC client-credentials flow) and call:

```bash
curl -sS --http1.1 -X POST "$GATEWAY/api/registration-tokens" \
  -H "Authorization: Bearer <jwt>" \
  -H "Content-Type: application/json" \
  -d '{"tenantId":"'"$TENANT_ID"'","autoApprove":true}'
# -> { "token": "sbt_…", ... }   (auto-approve skips the manual approval step)
```

> **Auth note (#431):** operator/control-plane endpoints require a JWT. The plaintext
> `X-Api-Key: <tenant-api-key>` shortcut works **only in non-Production** (a dev/test escape hatch) —
> in Production it is rejected with `403`. Device endpoints (registration handshake, heartbeat,
> desired-state, key rotation) still use the device's own credential and are unaffected.

## 2. (On the Pi) Build & run the agent

```bash
# Build for the Pi (ARM64). From the repo on a build host:
dotnet publish src/EdgeAgent/SignalBeam.EdgeAgent.Host -c Release -r linux-arm64 \
  --self-contained -o ./agent-arm64
# Copy ./agent-arm64 to the Pi, then on the Pi:

./SignalBeam.EdgeAgent.Host register \
  --tenant-id "$TENANT_ID" --token "$TOKEN" --cloud-url "$GATEWAY"
./SignalBeam.EdgeAgent.Host run
```

Or via Docker (mounts the Docker socket so the agent can manage containers):

```bash
docker run -d --name signalbeam-agent \
  -e Agent__CloudUrl="$GATEWAY" \
  -v /var/lib/signalbeam-agent:/var/lib/signalbeam-agent \
  -v /var/run/docker.sock:/var/run/docker.sock \
  ghcr.io/signalbeam-io/edge-agent:latest
```

## 3. Verify end-to-end

- **Registered:** `GET /api/devices/{id}` shows the device (status `Registered`/`Online` once heartbeating).
- **Heartbeats:** the dashboard / `GET /api/devices` shows a recent `lastSeenAt`.
- **Reconcile:** assign a bundle to the device's group, then confirm the agent pulls/starts the
  containers (`docker ps` on the Pi) and `GET /api/devices/{id}` reflects the bundle deployment status.

## Smoke-test from a dev machine (no Pi)

You can exercise the registration leg as a simulated device:

```bash
curl -sS --http1.1 -X POST "$GATEWAY/api/devices" \
  -H "Content-Type: application/json" \
  -d '{"name":"smoke-device","tenantId":"'"$TENANT_ID"'"}'
# -> 201 { "deviceId": "...", "status": "Pending", ... }
```

A `400 QUOTA_CHECK_ERROR` here means IdentityManager was cold and the quota check timed out —
retry; the retrying quota check (above) is the durable fix.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `400 INVALID_TENANT_ID` on register | No tenant in body and no valid API key → no tenant claim | Send `tenantId` in the body, or use a valid tenant API key |
| `400 QUOTA_CHECK_ERROR` (~10s) | IdentityManager cold-start exceeded the quota-check timeout | Retry; ensure the retrying quota-check fix is deployed |
| `HTTP/2 framing layer` error | ACA ingress / client HTTP/2 negotiation | Use `--http1.1` |
| Registration stuck `Pending` | Token was not auto-approve | Approve via dashboard, or issue an `autoApprove` token |
| No heartbeats after approval | Agent has no API key yet | Check `device-credentials.json`; claim-key runs after approval |
